# Weave production migration release

This repository owns the shared Platform migration history. The Weave application
repository supplies candidate SQL; a candidate there is not a hosted migration.
This release reconciles seven already-applied records and adds six reviewed
Weave candidates. Website application code and dependencies are unchanged.

## History reconciliation

Platform already records these versions. Do not apply them again:

- `20261108031732_weave_certified_private_access`
- `20261108032041_weave_platform_runtime_logins`
- `20261109045842_weave_matching`

The six non-credential records were restored from their recorded applied SQL.
The runtime-login record deliberately has a credential-free replay definition:
new environments create those roles as `NOLOGIN` and provision credentials
separately. Historical operator password literals are never copied into Git.
This does not change existing Platform logins or its migration records.

## New migrations

## Operator sequence

The user approved the original owner release and six migrations on 12 November
2026. Owner PR #21 merged as `0b68bf4`. Its first hosted application failed with
SQLSTATE `42501`: Platform's non-superuser operator cannot declare custom JWT
parameters in a function's `SET` clauses. The whole first migration rolled back;
Platform still records the same 16 versions and none of these six new versions.

The proposed repair captures the caller's JWT settings, uses transaction-local
settings for the checked actor, then restores the caller's settings on success or
rejection. It preserves the identity, session and workspace checks and grants no
new database privileges. The Weave candidate must receive the same repair.
The user separately approved the repair PRs, merges, release and hosted retry on
12 November 2026. That approval includes synchronization of the Weave candidate.

Apply only after owner review, passing checks and merge. Use the
merged owner checkout and verify the project ref before each hosted command.

The checked CLI version is 2.122.0; use its `--help` when using another version.
These commands select Platform explicitly and do not include seeds, role files,
Vault changes, authentication settings or credentials:

```sh
supabase migration list --project-ref ztygpuzldujfsqrubxic
supabase db push --project-ref ztygpuzldujfsqrubxic --dry-run --skip-vault
supabase db push --project-ref ztygpuzldujfsqrubxic --skip-vault
supabase migration list --project-ref ztygpuzldujfsqrubxic
```

The dry run must list exactly the six new versions above. Stop if any historical
version would be reapplied, another version is pending, or the remote has changed.
Use existing authorized CLI authentication; never put a database password in a
command, file, commit or log. Check migration history and grants after application.
Do not substitute a second migration history generated by another repository.

Keep `private.weave_matching_retrieval_settings.hybrid_enabled` false. The API's
dedicated runtime roles, state/signing keys, Certified consent, Auth callbacks and
production app configuration are separate operator steps. Schema installation does
not establish a working sign-in or real-user acceptance.

## Verification and recovery

The disposable SQL baseline models Certified identities, JWT expiry, banned and
anonymous users. CI uses Supabase PostgreSQL 17 with pgvector and creates a clean
database from `template0`, avoiding the image's preinstalled Auth schemas. All
website SQL tests still run, including steward access and email-delivery boundaries.

Local proof for the repair: all 22 migrations replayed under a non-superuser
migration owner, without JWT parameter grants; all ten owner SQL suites passed.
The new context suite checks successful and rejected commands and empty caller
context. Website syntax checks, 88 fixture tests and HTTP smoke passed for PR #21.
The exact CI image, TCP password authentication and fresh-database bootstrap were
exercised separately. CI now uses the non-superuser migration owner too.
Weave's separate local PostgreSQL suites passed 28 tests covering discovery,
invitations, private team saves, two-owner share/edit/withdraw, public snapshots,
index retrieval and public support lifecycle. They use synthetic providers and
identities; they are not real Certified or hosted Auth acceptance.

Independent review covered the original 13 restored/new migrations and the repair's
context restoration, failure paths, CI and regression proof. The remaining provenance
documentation finding is addressed here. Revised hosted application and browser
acceptance have not run.

Each migration is transactional. A failed migration rolls back; diagnose it before
retrying. After successful team writes, disable project actions and repair forward
through a reviewed migration. Do not drop saved initiatives, grants or shared
Platform data as a rollback. The prior preview's direct matching RPC path is
intentionally revoked; the workspace-aware Weave API must accompany this schema.

## Saved-card deletion release

`20261117200140_weave_initiative_deletion` matches
`supabase/candidates/weave-initiative-deletion.sql` in Weave `main` (`024d713`) byte
for byte. It adds `weave.delete_initiative`, which lets an owner delete one personal
saved card at the exact revision they saw, and a tombstone table so a deleted ID never
returns. It refuses a card that anything else refers to, and it never deletes team
documents. Weave's `POST /api/account` action `delete` calls it, and that API has been
in production since `024d713`. Until this migration is applied, deleting a card fails there.

The user approved applying it to Platform on 17 November 2026. Use the same commands
as above. The dry run must list exactly this one version. Afterwards, check that
`weave.delete_initiative(uuid, integer, uuid)` is executable by `authenticated` only
and that `private.weave_deleted_initiatives` has row-level security and no client grants.

## Project grant pruning record

`20261123095853_weave_project_oauth_pruning` records
`supabase/candidates/weave-project-oauth-pruning.sql` in Weave `develop` (`239398e`). It schedules
the pg_cron job `weave-project-oauth-prune`, which deletes expired rows from
`weave_project_oauth.records` daily at 03:17 UTC, so a lapsed session's encrypted grant does not stay in
the database.

The job was applied to Platform on 23 November 2026 as plain SQL, as `postgres`, before this file
existed, so Platform runs it (job 1, active) while its migration history does not list this version.
The file differs from the candidate in one way: its statements sit in a block that schedules nothing
outside the database pg_cron serves, because pg_cron refuses to install anywhere else and CI replays
migrations into `regen_test`. The block also refuses to schedule the job as a role that is neither
the table's owner nor exempt from row-level security, whose job would delete nothing, and checks that
exactly one job has the name afterwards. On Platform, `cron.schedule` with the same name and role
updates job 1 in place, so applying the file again changes nothing.

To record it, either apply it with the commands above (the dry run must list exactly this one
version), or mark it applied without running it:

```sh
supabase migration repair --project-ref ztygpuzldujfsqrubxic --status applied 20261123095853
```

Afterwards, `select jobid, schedule, command, username, active from cron.job where jobname =
'weave-project-oauth-prune'` must return one row: job 1, `17 3 * * *`, run as `postgres`, active.

## Saved-card deletion: stale references release

`20261126041522_weave_initiative_deletion_stale_references` matches
`supabase/candidates/weave-initiative-deletion-stale-references.sql` in Weave
([regen-commons/weave#274](https://github.com/regen-commons/weave/pull/274), `7cb0b24`) byte for
byte. It replaces `private.weave_delete_initiative` with `create or replace`, so the function keeps
its owner and grants, and it refuses to run before `20261117200140_weave_initiative_deletion`.
Weave's matching API serves project workspaces only, so a personal saved card can no longer withdraw
its sharing, clear its saved partners or let its query vectors be pruned first. These references no
longer stop an owner deleting a personal card; each is deleted with it:

- A project setup that finished (`linked`) or was marked `group_rejected`. A setup still under way is
  refused as before. `group_rejected` also follows a timeout or server error, after which a group may
  exist on Certified under the setup's handle; deleting the card removes that record of the handle.
- The card's own needs and offers shared for matching. A personal card is never in matching, which
  needs a project link, so other people see no change: their saved partners naming an entry already
  read as unavailable, and their rows stay.
- The owner's saved and dismissed partners for the card, and the query vectors derived from its entries.

Every other refusal and the owner, revision and retry checks are unchanged. Platform's function
matched `20261117200140_weave_initiative_deletion` exactly on 26 November 2026. The Weave API needs
no change; the app's refusal message from the same pull request no longer names sharing or partners.

Applying it to Platform is not yet approved. Merge only after regen-commons/weave#274 has had its
second review, and apply only with the user's separate approval, using the same commands as above.
The dry run must list exactly this one version. Afterwards, check that
`private.weave_delete_initiative(uuid, integer, uuid)` is still executable by `authenticated`
only and that `weave.delete_initiative(uuid, integer, uuid)` is unchanged.

## Public support listings read release

`20261127085818_weave_public_support_listings` matches
`supabase/candidates/weave-public-support-listings.sql` in Weave
([regen-commons/weave#272](https://github.com/regen-commons/weave/pull/272), `dd3365d`) byte for
byte. It adds `private.weave_public_support_listings(text)`, a `security definer` function with an
empty search path. For one project it returns the needs and offers Weave published and confirmed by
reading them back, still open and unexpired, from a project link that is not paused: each record's
kind, record key, address, CID and the public record itself, and nothing private. Only
`weave_index_job` may run it; `public`, `anon`, `authenticated`, `service_role` and
`weave_workspace_runtime` may not. It refuses to run before `weave_workspace.support_listings`,
`weave_workspace.project_links` and the `weave_index_job` role exist.

Weave's public initiative page reads its listings through this function
(`GET /api/public-initiative`, from regen-commons/weave#272). Platform does not have it, so that
read fails, and Weave answers `public_initiative_unavailable`. This is inferred from the code and
was not observed in production. On 26 November 2026 Platform held 8 published listings, 4 needs and
4 offers, that no page could show. The two-place decision for needs and offers (DL-155, in
[regen-commons/weave#278](https://github.com/regen-commons/weave/pull/278)) keeps this read:
under D47 Weave reads published listings from its own record first.

On 27 November 2026 Platform had the role and the `repository_did` and `matching_paused` columns the
function needs, and not the function. The user approved applying it to Platform on 27 November
2026, once its review passed. The Supabase CLI was not available, so it was applied through the
Supabase connector, as on 21 November, and the file takes the version the connector recorded. The
SQL recorded in Platform's history matches the file byte for byte (SHA-256 `d26094d2...8bee7f`).
Afterwards only `weave_index_job` could execute it, from this check:

```sql
select r, has_function_privilege(r, 'private.weave_public_support_listings(text)', 'execute')
from unnest(array['weave_index_job', 'anon', 'authenticated', 'service_role', 'weave_workspace_runtime']) r;
```

Only the first row read `true`. The function then returned all 8 published listings, for the one
project that has them. `supabase/tests/weave-public-support-listings.sql` proves the function's
filters and grants on the CI image: confirmed, open and unexpired listings for exactly the asked
project are shown, and pending, withdrawn, conflicting, expired, malformed, closed, mismatched and
paused ones are not.
